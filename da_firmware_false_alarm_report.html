▎異常現象

客戶在 signage_configure.json 設定 PackageName / ActivityName 後，機器開機時顯示 「DA ver:0. Please update DA firmware.」，沒有進入客戶自家的 app，接著直接關機。

▎最終判斷

這不是 DA 韌體真的過舊，也不是 PackageName / ActivityName 設定值本身有錯。整條失敗鏈的起點在客戶 app，不在 nSignage：

  • nSignage 依 config 拉起客戶 app com.idroid.epdplayerv2 後自行退出。
  • 客戶 app 自家的 ScheduleHealthMonitor watchdog 判定「調度系統已閒置超過 120 秒」，呼叫 Process.killProcess(myPid()) 自殺（SIGKILL 是它自己發的，不是系統回收）。
  • 它的「自我重啟」實作有缺陷：先 startActivity() 再立刻 killProcess()，剛啟動的 Activity 隨 process 一起死，重啟失敗。
  • 前景 Activity 消失，Android 回退 resume HOME —— 而 HOME 就是 nSignage → nSignage 被拉回並開始 initDASpi() / initEpd()。
  • 同時系統重啟客戶 app 的 AutoStartService，客戶 app 1 秒後復活，在 nSignage init 完 0.4 秒後呼叫 uninitEpd()，兩個 process 並行操作同一組 SPI。
  • DA 進入 not-ready 狀態，nSignage 讀取版本時發生 DA_GetStatus GetRdyTimeout。
  • DA_VERSION 回傳空值 "0"，checkIfUpdateDA() 無法分辨「讀取失敗」與「韌體過舊」，誤判為需更新韌體。
  • 顯示錯誤畫面後執行 runPowerOffUpdateEpdBuffer()，直接關機。

5 Root Cause 分析

▎直接原因：checkIfUpdateDA() 無法區分「讀取失敗」與「韌體過舊」

位置：MainActivity.java:7970-8004

private boolean checkIfUpdateDA() {
    boolean result = false;
    try {
        if (!TextUtils.isEmpty(RuntimeValue.DA_VERSION)) {
            String[] daVerSplits = RuntimeValue.DA_VERSION.split(",");

            if (daVerSplits.length < 3) {
                result = true;      // ← "0" 只切出 1 段，直接判定要更新韌體
            }
            ...
        }
    }
    catch (Exception e) { ... }
    ALog.info("checkIfUpdateDA result: " + result);
    return result;
}

DA_VERSION = "0" 不是空字串，通過 isEmpty() 檢查；split(",") 長度為 1，小於 3 → result = true。程式沒有任何機制辨識「這是一次失敗的讀取」。

▎直接原因：誤判後直接關機，無重試

位置：MainActivity.java:2797-2812。判定為 true 後立即產生錯誤圖並呼叫 mEpdController.runPowerOffUpdateEpdBuffer()，沒有重試 DA init 的機會，使用者只能看到錯誤畫面與關機。

▎根本原因（起點）：客戶 App 的 watchdog 自殺

EPDPlayer_ScheduleHealthMonitor 是客戶 app 自帶的健康監控。它在調度器閒置超過 120 秒時判定系統異常，並執行「自我重啟」：

08:57:17.752  啟動調度健康監控                  ← watchdog 上線 (TID 1800)
08:57:21 ~ 08:59:17                            ← 2 分鐘內「零」調度執行 log
08:58:17.754  寬限期結束，開始監控調度健康狀態
08:59:17.766  調度系統已閒置超過 120 秒
08:59:17.767  調度系統異常，準備重啟應用
08:59:17.777  調度系統失敗次數: 6              ← 累計第 6 次
08:59:19.778  執行應用重啟...
08:59:19.945  Process : Sending signal. PID: 1764 SIG: 9   ← 自殺

關鍵在於：「每分鐘快速循環」(quick_cycle_automation) 規則明明顯示 調度已安排，但排定後 2 分鐘內一次都沒有執行。這是觸發 watchdog 的唯一條件，屬於客戶 app 內部問題，需由客戶端釐清。

▎根本原因（放大）：自我重啟實作不可靠

客戶 app 的重啟流程是「startActivity() → 立刻 killProcess(myPid())」。新啟動的 Activity 還沒完成建立就隨 process 一起被殺（log 中的 WIN DEATH），重啟實際上失敗了。

後果是 Android 找不到前景 Activity，回退去 resume HOME —— 而 HOME 正是 nSignage。同時系統又以 Scheduling restart of crashed service 在 1 秒後把客戶 app 的 AutoStartService 拉回。這正是造成「兩個 app 同時活著、同時搶 SPI」的直接機制。

▎根本原因：SPI / DA 被兩個 process 同時存取

客戶 app com.idroid.epdplayerv2 也整合了 signage SDK（log 中可見其專屬的 signageSDK: SlideShowService），會直接對 SPI 下 uninitEpd() / epd_init。當它與 nSignage 同時存活時，兩者對同一顆 DA 下指令，導致 DA 狀態機被打亂而進入 not-ready。

目前 SPI 存取只有 process 內的 DA_AppLockMutex，沒有跨 process 的互斥保護。

▎根本原因：交棒模型不穩

設定 PackageName / ActivityName 後，nSignage 拉起客戶 app 便自行退出。但 nSignage 是 launcher/home，一旦客戶 app 異常退出（本次為它自己的 watchdog 自殺），Android 會把 nSignage 拉回前景，而客戶 app 的 AutoStartService 也會同時把自己拉起 —— 兩者同時活著並各自 init SPI。這條路徑在正常交棒時不會發生，只在客戶 app 異常退出時觸發，因此呈現為偶發性問題。

▎發生頻率

8 份 logcat 中有 3 份（logcat.1 / logcat.6 / logcat.8）出現 執行應用重啟；且 app 內部計數器已累計到 調度系統失敗次數: 6。這是反覆發生的問題，不是單次偶發。只是並非每次自殺都剛好撞上 nSignage 的 DA init 時間窗，所以不是每次都會關機。

6 非主要原因排除
項目判斷原因
DA 韌體真的過舊 非主因 同一台機器六次開機，五次都正確讀到 0.1.0.23_31.5 / Apr 1 2026，遠新於門檻 2024/12/20。
PackageName / ActivityName 設定值錯誤 非主因 checkIfUpdateDA() 在 getConfigFile() 之前執行（2797 行 vs 2815 行），判斷當下根本還沒讀到這兩個欄位。它是間接觸發條件，不是直接原因。
LowMemoryKiller 殺掉客戶 app 非主因 log 中無 LMK / kill 相關訊息，且 SIGKILL 的發訊者就是被殺者自己（PID 1764 → PID 1764）。
ANR / Native crash 導致客戶 app 死亡 非主因 無 ANR、無 tombstone、無 FATAL EXCEPTION。是 app 主動呼叫 Process.killProcess(myPid())。
nSignage 主動殺掉客戶 app 非主因 SIGKILL 發生於 08:59:19.945，而 nSignage (PID 1200) 早在 08:57:06 就已退出，當下根本不存在。
外接 SD 卡 / update_da_fw.json 非主因 log 顯示 Ext-SD File update_da_fw.json not exist、EXTERNAL_SDCARD_PATH 為空，hasUpdateDa = false，並未走 DA 更新流程。
RIL / ttyACM1 錯誤訊息 旁支噪音 opening base channel device - /dev/ttyACM1. retrying... 全程持續出現（含正常開機），與 DA SPI 無關。

7 建議修正方向

▎修正 1（短期・低風險）：DA 版本讀取失敗防呆

讀不到版本時不應視為「韌體過舊」。建議在 checkIfUpdateDA() 前置判斷：

private boolean checkIfUpdateDA() {
    // DA 通訊失敗時 DA_VERSION 會是 "0"，此時不可判定為韌體過舊
    if (TextUtils.isEmpty(RuntimeValue.DA_VERSION)
            || "0".equals(RuntimeValue.DA_VERSION.trim())) {
        ALog.error("DA version read failed, skip firmware check.");
        return false;
    }
    ...
}

▎修正 2（短期）：DA init 失敗時重試而非關機

在 ACTION_EPD_INIT 收到空的 DA_VERSION 或 DA_MAC_ADDRESS 時，重跑一次 DA init（建議上限 2～3 次）再做韌體判斷；仍失敗才顯示錯誤，且應顯示「DA 通訊失敗」而非「請更新韌體」，避免誤導現場人員。

▎修正 3（根本）：DA / SPI 存取集中化

  • 將 DA / EPD 的 SPI 存取集中到單一 service（例如統一透過 McuATCmdService 代理），禁止多個 app 各自 initDASpi() / uninitEpd()。
  • 或在 SDK 層加入跨 process 互斥（file lock / binder service），確保同一時間只有一個 process 能操作 SPI。
  • 目前的 DA_AppLockMutex 僅限 process 內，無法防止本次情境。

▎修正 4（根本）：釐清交棒生命週期

  • nSignage 拉起客戶 app 前，確實釋放 SPI 並確保自己不會被系統重新拉回前景。
  • 或反過來：nSignage 常駐並保有 SPI，客戶 app 不直接碰 SPI，改由 nSignage 代為刷圖。

▎需客戶端處理（整條鏈的起點）

  • 查明 quick_cycle_automation 為何排定後不執行。規則顯示 調度已安排，但 2 分鐘內零執行紀錄。這是 ScheduleHealthMonitor 觸發的唯一條件，也是整起問題的源頭。可先確認調度是走 AlarmManager、Handler 還是 WorkManager，以及是否受 Doze / 精確鬧鐘權限影響。
  • 修正自我重啟的實作。目前「startActivity() → 立刻 killProcess()」會讓新 Activity 隨 process 一起死，重啟必定失敗並把 HOME 叫回前景。建議改用 AlarmManager.setExact() 排定延遲重啟後再 killProcess()，或直接改為重置調度器而不殺 process。
  • watchdog 加上退避機制。目前失敗次數已累計到 6 次仍持續自殺重啟，形成循環。建議連續失敗達門檻後停止自殺，改為記錄或降級運作。
  • app 結束前應釋放 SPI。若仍需自我重啟，務必在 killProcess() 前呼叫 uninitEpd() 並確認已交還 SPI，避免留下半初始化的 DA 狀態。
8 建議檢查項目

▎檢查 1：確認是否有兩個 process 同時操作 SPI

adb logcat -b all | grep -E "ntxSpi|signageSDK|SignageAAR" | awk '{print $3}' | sort | uniq -c

▎檢查 2：追蹤 DA 讀取失敗與誤判

adb logcat -b all | grep -E "GetRdyTimeout|DA_VERSION|checkIfUpdateDA|should update DA firmware"

▎檢查 3：確認客戶 app 被殺與 nSignage 被重拉的時機

adb logcat -b all | grep -E "Start proc|has died|exited due to signal|uninitEpd|initDASpi"

▎檢查 4：追蹤客戶 app 的 watchdog 自殺（整條鏈起點）

adb logcat -b all | grep -E "ScheduleHealthMonitor|執行應用重啟|Sending signal.*SIG: 9|AutomationScheduler"

確認要點：Sending signal. PID: X SIG: 9 中的 PID 若與被殺的 PID 相同，即為 app 自殺而非系統回收。

9 最終結論

目前 log 已可確認：DA 韌體並沒有問題，是 nSignage 讀不到 DA 版本後誤判成「韌體過舊」而主動關機。同一台機器六次開機，五次都正確讀到 0.1.0.23_31.5 (Apr 1 2026)，僅失敗的那次因 DA_GetStatus GetRdyTimeout 讀回空值 "0"。

而完整的因果鏈，起點在客戶 app，不在 nSignage：

客戶 app 調度器排定規則卻不執行
    → 自家 ScheduleHealthMonitor 判定異常 (閒置 > 120s)
    → Process.killProcess(myPid()) 自殺 (SIG 9)
    → 自我重啟失敗 (startActivity 後立刻 kill)
    → Android 回退 resume HOME = nSignage
    → nSignage 開始 initDASpi() / initEpd()
    → 客戶 app 的 AutoStartService 1 秒後被系統拉回
    → 客戶 app 呼叫 uninitEpd()，兩 process 搶同一組 SPI
    → DA not-ready → GetRdyTimeout → DA_VERSION:0
    → nSignage checkIfUpdateDA() 誤判為韌體過舊
    → 顯示 "Please update DA firmware." → 關機
