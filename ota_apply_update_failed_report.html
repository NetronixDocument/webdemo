OTA apply update failed 成因分析報告

針對客戶機台更新時跳出「apply update failed」對話框的可能原因盤點（無法取得 log 之推論版）
模組：packages/apps/upgrade_OTA
機種：E70P24_android · Android 12 · Virtual A/B
觸發點：僅 2 處
可能原因：13 項
1 問題摘要
高可能性
中可能性
低可能性
可直接排除

異常現象

客戶機台執行 OTA 更新，進度條停在起始階段後跳出對話框，內容為英文小字 apply update failed，下方為「取消 / 確定」兩個按鈕，按下後直接結束更新流程。

關鍵結論

這句話不是資源字串，是 CopyPackageActivity.java:151-185 依 msg.arg1 動態組出來的（"apply update" + " failed"），只對應唯一一個錯誤碼 UPDATE_APPLY_PACKAGE_FAILED (213)。

  • 213 代表 payload 根本還沒送進 update_engine —— 失敗發生在 App 端解 zip、開檔、或呼叫 applyPayload() 的當下。
  • update_engine 真的開始寫入之後才失敗的情況，錯誤碼是 214，畫面顯示的是純 update failed（沒有 apply 這個字）。
  • 因此光憑截圖上有沒有 apply，就能把嫌疑範圍砍掉一半。

判讀口訣：有 apply → 封包 / 檔案 / update_engine 狀態問題。沒有 apply → 簽章、空間、分區、verity 等真正的燒錄問題。

2 四種失敗訊息對照
arg1常數名稱畫面顯示文字實際會不會發生
212 UPDATE_VERIFY_PACKAGE_FAILED verify file failed 不可能 　verifyPackage() 是死碼，onCreate 直接送 APPLY
213 UPDATE_APPLY_PACKAGE_FAILED apply update failed 本次案例 　payload 未進入 update_engine
214 UPDATE_PROGRESS_REFRESH_FAILED update failed 另一種 　update_engine 跑完後回報失敗
215 UPDATE_APPLY_REBOOT_FAILED reboot failed 不可能 　程式中沒有任何地方送出此碼
3 失敗發生的位置

整條更新路徑分成三段，213 只會發生在前兩段：

段 1 · App 開檔
openFileDescriptor
用 MediaStore 的 content:// uri
以 "rw" 模式開啟 OTA 包
段 2 · App 解 zip
ZipInputStream 掃描
找 metadata 取 payload 偏移
找 payload_properties.txt 取 headers
段 3 · 燒錄
update_engine
實際寫入 A/B slot
此段失敗顯示的是 update failed
↓
// CopyPackageActivity.applyUpdate() — 213 的兩個發送點 pfd = openFileDescriptor(uri, "rw"); ← 拋 IOException → 213 zis = new ZipInputStream(...); while ((ze = zis.getNextEntry()) != null) { ← 讀取途中 IOException → 213 if ("META-INF/com/android/metadata") 解析 payload.bin 偏移 if ("payload_properties.txt") 取得 headers } if (mHeaderKeyValuePairs == null) ← 找不到 → 213（不拋例外，安靜跳窗） mUpdateEngine.applyPayload(afd, headers); ← ServiceSpecificException → 213 ← 訊息含 reboot + applied → 視為成功，去重開機 onPayloadApplicationComplete(errCode != 0) ← 這裡才是 214「update failed」
4 可能原因 A：OTA 封包內容不符預期

觸發條件：zip 掃不到根目錄的 payload_properties.txt，導致 mHeaderKeyValuePairs == null。

這條路徑不會拋例外、不會 FC，安靜地跳出這個對話框 —— 嫌疑最大。

#原因為什麼會變成這句話可能性
1 下載檔案不完整／被截斷 程式只檢查 File.exists()，沒檢查大小或 checksum。getNextEntry() 讀到截斷點只是回 null，迴圈靜靜結束 高
2 儲存空間不足導致寫入截斷 下載中途空間耗盡，檔案存在但內容不完整，表現與 #1 完全相同 高
3 Server 回的是 HTML 錯誤頁或轉址頁 DownloadManager 照樣把回應存成檔案，exists() 成立但根本不是 zip 中
4 客戶自行解壓後重新壓縮 比對是 equals() 完全相等，一旦變成 update/payload_properties.txt 這種頂層資料夾就找不到 高
5 放錯包 非 A/B 的舊版 update.zip、全志 PhoenixSuit 的 img 包、或其他機種的包 —— 根本沒有 payload.bin / payload_properties.txt 高
6 用 Windows 內建壓縮工具重打包 entry 名稱使用反斜線或不同編碼，字串比對失敗，同 #4 低
5 可能原因 B：檔案存取失敗

觸發條件：openFileDescriptor(uri, "rw") 或串流讀取途中拋出 IOException。

#原因為什麼會變成這句話可能性
7 MediaStore uri 失效 uri 是 MediaScannerConnection.scanFile 掃出來的。檔案被重新下載覆寫、或被 DownloadManager.remove() 刪過後，舊 row 已無效 → FileNotFoundException 高
8 本機更新時來源是唯讀媒體 App 用 "rw" 模式開檔（讀 OTA 包其實只需 "r"）。SD 卡／USB 以唯讀掛載、或檔案屬性唯讀，就會開檔失敗 中
9 檔案位於 MediaScanner 掃不到的路徑 例如 App 私有目錄或 /data 底下，掃描結果無對應 MediaStore 記錄 低
10 儲存媒體 I/O 錯誤 SD 卡壞塊、接觸不良、CRC 不符，讀到一半拋 IOException 中
6 可能原因 C：update_engine 狀態不對

觸發條件：applyPayload() 拋出 ServiceSpecificException。update_engine 在 ApplyPayload 進入點只有以下幾個擋關（update_attempter_android.cc）。

#update_engine 回傳的訊息觸發情境可能性
11 Already processing an update,
cancel it first.		 前一次 OTA 中斷（拔電、當機、使用者按返回離開更新畫面）後沒重開機；或使用者連按兩次；或 DownloadOTAService 已先觸發過一次。這是「重開機後就好了」型的客訴 高
12 Passed invalid header: ... payload_properties.txt 被改成 CRLF 換行、或含空行／多餘空白 —— 程式用 split("[\n\t ]") 會切出不含 = 的 token 中
13 Passed repeated key: ... 同 #12，重打包過程中內容被改壞導致重複鍵 低

注意：An update already applied, waiting for reboot 不會跳這個對話框 —— 程式特意判斷訊息中同時含 reboot 與 applied 時視為成功，直接進入重開機流程。

7 可直接排除的方向

因為 213 發生在 applyPayload() 呼叫成功之前，以下情況全部不可能是這句話的原因 —— 它們都走 onPayloadApplicationComplete(errCode != 0)，畫面上會是純 update failed：

  • payload 簽章不符 / update-payload-key.pub.pem 金鑰對不上 排除
  • A/B slot 空間不足、super 分區 CoW 配置失敗 排除
  • build timestamp 倒退（kPayloadTimestampError） 排除
  • metadata hash / FILE_HASH 驗證不符 排除
  • dm-verity 寫入失敗、post-install script 失敗 排除
  • 分區清單不符（ab_partitions.txt 對不上） 排除
8 無法取得 log 時的側面判別
可請客戶回報的現象指向
進度條到起始階段後幾秒內就跳窗 原因 B（開檔就失敗），或 #11 update_engine 狀態
停在起始階段很久（數十秒～數分鐘）才跳窗 原因 A —— App 必須把整包串流讀完才會發現缺少 payload_properties.txt
等待時間比正常明顯短就跳窗 高度指向截斷檔（#1 / #2）
重開機後再試就成功 #11 Already processing an update
永遠停在起始階段、完全不跳窗 不是本案 —— 是 pfd == null 的靜默 return（另一個缺陷）

最有效的一步

請客戶回報裝置上 OTA 檔案的實際大小，與我方 build 產出的 update.zip 對照。一致即可一口氣排除原因 A 的 #1～#3，把範圍縮到 4 項以內。

9 已驗證事項

我方 build 產出的 OTA 包本身正常

已實際拆解 out/target/product/E70P24_android/update.zip 確認：

  • ota-type=AB，legacy META-INF/com/android/metadata 有正常寫入。
  • payload.bin 與 payload_properties.txt 皆位於 zip 根目錄，名稱正確。
  • ota-property-files 與 ota-streaming-property-files 給的 payload.bin 偏移／大小完全相同 —— 程式「最後一筆勝出」的解析寫法在此碰巧不會出錯。
  • payload 大小未超過 Integer 上限，目前不會觸發溢位問題。
  • 機台為 virtual_ab=true / ab_update=true，走 UpdateEngine 路徑正確。

結論：問題不在 build 產物，而在客戶端的檔案狀態或 update_engine 狀態。

10 附帶發現的程式缺陷

本次追查最大的阻礙是：App 把所有前置失敗壓成同一句話，且完全不記錄原因。以下缺陷會直接造成 FC 或卡死（而非跳窗），建議一併排入修正：

位置缺陷後果
catch 區塊 getLocalizedMessage() 未判 null 就呼叫 contains() 訊息為 null 時 NPE
catch 區塊 未涵蓋 SecurityException / NumberFormatException / NegativeArraySizeException 直接 FC，客戶看到的是閃退而非錯誤訊息
pfd == null 直接 return，未送出任何失敗訊息 畫面永遠卡在起始進度
extractText() read() 回 -1 時 count 會變負數 IndexOutOfBoundsException
偏移解析 使用 Integer.parseInt OTA 包一旦超過 2 GB 即溢位崩潰
zip 掃描迴圈 找到目標後沒有 break 需串流讀完整包才呼叫 applyPayload；期間使用者按返回會觸發 unbind()

建議的最小修正

在兩個 213 發送點補上 Log.e(TAG, ..., e)，並把真實例外訊息帶進對話框。只加 log 不動邏輯，不影響現有行為，但下次客戶回報時即可一眼定位到上述 13 項中的哪一項。
