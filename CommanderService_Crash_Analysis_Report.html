▎異常現象

系統開機後建立 com.ari_os.commander.CommanderService，Hilt/Dagger 在注入 CommanderServer 相依物件時建立 BluetoothNameMonitor，其建構子第 28 行對一個 null 物件呼叫 getClass()，導致主執行緒發生未捕捉的 NullPointerException，Service 建立失敗並使程序崩潰。

▎目前可確認的結論

  • 直接 crash 點位於 BluetoothNameMonitor.<init>(SourceFile:28)。
  • CommanderService.onCreate() 只是觸發依賴注入，並非最底層故障位置。
  • 從現有 stack trace 無法唯一判定是哪一個變數為 null；必須查看反編譯後第 28 行或原始碼。
  • 最可能是藍牙相關 service、manager、adapter 或裝置名稱來源在開機早期尚未可用，程式又未做 null 防護。

4 Root Cause 分析

▎直接原因：BluetoothNameMonitor 建構子缺少 null 防護

第 28 行對 null 物件呼叫 getClass()。不論 null 的來源為何，程式在建構階段沒有檢查相依物件是否可用，是本次 crash 的直接原因。

▎高機率根因 1：BluetoothAdapter 或 BluetoothManager 尚未可用

CommanderService 若於開機早期或 Direct Boot 階段啟動，藍牙 framework service 可能尚未 ready；例如 getSystemService(BluetoothManager.class) 或 BluetoothAdapter.getDefaultAdapter() 回傳 null，後續反射或型別操作便會觸發此錯誤。

▎高機率根因 2：裝置未宣告藍牙 feature，或產品裁切造成 service 缺失

若 system image 與 vendor image 的藍牙設定不一致，或產品設定未包含完整 Bluetooth service / feature，應用程式取得的藍牙物件可能為 null。需比對可正常運作機種的 product packages、feature XML 與 framework overlay。

▎可能根因 3：RealWear / Archer 專用 API 在目前 AOSP 不存在

此 APK 可能假設特定 OEM framework、system service 或客製 Bluetooth API 必定存在。若 MTK Android 16 映像未整合相同元件，反射取得 class 或 service 的結果可能為 null。

▎權限不是目前最像的直接原因

若缺少 BLUETOOTH_CONNECT 等執行權限，常見結果通常是 SecurityException。本次明確為 null 解參考，因此應先查第 28 行資料來源，再確認權限。

5 與其他問題的界線
項目是否為本次主因說明
APK 使用 PRESIGNED 無直接證據 簽章錯誤通常發生在安裝或 shared UID 驗證階段；本次 APK 已成功啟動程序並進入 Service。
sharedUserId=android.uid.system 簽章不相容 另一個問題 會造成 INSTALL_FAILED_SHARED_USER_INCOMPATIBLE，與本次執行期 NPE 不同。
ACS 背景啟動前景 Service 被拒絕 另一個問題 ForegroundServiceStartNotAllowedException 是 Android 背景啟動限制，與 Commander 的 BluetoothNameMonitor NPE 無關。
Hilt / Dagger 觸發路徑 Hilt 只是建構相依物件；真正的錯誤仍在 BluetoothNameMonitor 的應用程式碼。

7 建議修正方向

▎原始碼可修改時

  • 不要在 DI 建構子內假設 Bluetooth service 已 ready；將初始化移到明確的生命週期方法。
  • 對 BluetoothManager、BluetoothAdapter、裝置名稱及反射回傳值做 null 檢查。
  • 若藍牙尚未可用，註冊狀態監聽，等待 service ready 或 Adapter 進入 ON 後再初始化。
  • 將可恢復的初始化失敗記錄為 warning，採有限次數 retry，避免主執行緒直接 crash。
// 示意：實際 API 請依第 28 行程式碼調整
BluetoothManager manager = context.getSystemService(BluetoothManager.class);
if (manager == null) {
    Log.w(TAG, "BluetoothManager is not available; defer initialization");
    return;
}

BluetoothAdapter adapter = manager.getAdapter();
if (adapter == null) {
    Log.w(TAG, "BluetoothAdapter is not available; defer initialization");
    return;
}

// Adapter ready 後再建立 monitor，並避免對任何 nullable 值直接呼叫 getClass()

▎只有預編譯 APK、無原始碼時

  • 向 APK 供應商取得支援 Android 16、目前 MTK BSP 與該硬體平台的版本。
  • 確認供應商要求的 OEM framework、privileged permissions、shared library、feature XML 與開機服務均已整合。
  • 不建議只修改 AOSP framework 讓 null 物件變成非 null；若缺的是 OEM 私有介面，應補齊正式相依元件或更新 APK。
8 驗證標準與最終結論

▎修正後驗證標準

  • 開機後不再出現 Unable to create service CommanderService。
  • com.ari_os.commander 不會持續 crash/restart。
  • BluetoothNameMonitor 在藍牙關閉、未 ready、無硬體或 service 重啟時仍不會崩潰。
  • Commander 功能可在冷開機、重新開機及藍牙開關切換後正常運作。

▎最終結論

目前 log 已可確認：CommanderService 的直接 crash 原因，是 BluetoothNameMonitor 建構子第 28 行對 null 物件呼叫 getClass()。最優先工作不是修改 Service 權限，而是反編譯或取得原始碼，確認第 28 行是哪一個藍牙相依物件為 null。

建議處理順序：

  1. 先定位 BluetoothNameMonitor SourceFile:28。
  2. 同時確認 bluetooth_manager、Bluetooth feature 與 Adapter 狀態。
  3. 加入 null 防護與延後初始化機制。
  4. 若 APK 為第三方 prebuilt，取得 Android 16 / MTK 相容版本並補齊 OEM 相依元件。
